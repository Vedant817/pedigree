## 5. Findings

### F1 — uvicorn transport access log (open question, not verified at the wire)
The interrupted pass started the service on port 8022 and confirmed that the
application's own `pedigree.access` lines are templated and credential-free. It did
**not** settle whether the transport's own access log (the `python -m pedigree.cli serve`
command uses uvicorn at info level) echoes the raw request URI including a query
string such as `?token=…`. If it does, that is a low-severity leak path when a
client puts a credential in a query string (tokens are documented to travel in the
`Authorization` header, which is never logged). **Status: not verified; record as a
residual limit.** The application log itself is clean.

### F2 — Documentation drift (pre-existing on `main`, not caused by P-022)
1. `docs/02-ARCHITECTURE.md:98` lists metric series that do not exist
   (`pedigree_requests_total`, `pedigree_request_seconds`, `pedigree_rate_limited_total`)
   and labels that do not match (`{state}`, `{tenant}` vs. the actual `{status}` and
   `{tenant,status}`); also says `pedigree_nodes{tenant}` (top-N) rather than the
   `{tenant,status}` gauge.
2. `AUDIT.md:68` and `:140` still describe `/metrics` as unauthenticated and the
   tool-call trace as absent — both are fixed by P-022.
3. `docs/01-IDEA.md:188` says *all* MCP responses carry `trace`; the implementation
   returns it only on the four judged tools (`pedigree_revoke`, `pedigree_blame`,
   `pedigree_impact`, `pedigree_check_action`), per the spec.

These are recorded as findings; fixing them is a documentation task, not a code
change for this feature.
