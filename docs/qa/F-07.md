## Finding (fixed)

- **M1 (medium, fixed):** `LIMITS["events_per_request"] = 500` existed in config but nothing
  enforced it, so a single request could carry an unbounded number of graph operations (only the
  256 KB body cap applied). Fix: `ingest_events` raises typed `TooLarge` (413, `too_large`) with the
  limit in `detail`; regression test `test_events_rejects_oversized_batch` (501 events).

## Residual risks (documented, not fixed)

- `/v1/events` applies operations in order and **aborts on the first typed error**, so a failing
  batch leaves the earlier events applied (no cross-event atomicity). Acceptable for an idempotent
  capture channel; recorded in `docs/KNOWN_ISSUES.md`.
- `BodySizeMiddleware` compares against a literal `256 * 1024` rather than `LIMITS["body_bytes"]`
  (same value); cosmetic.
- Runtime allow-list (`claude-code`, `opencode`, `generic`) is silent coercion, not validation -
  the caller cannot pass an arbitrary runtime string into the graph.

**Verdict: PASS.**
