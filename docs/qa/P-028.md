- Fault origin is the database host: `GRAPH.COPY failed, could not fork` is a

  failed expect the successful-copy path.
- The dev DB (`pedigree-db`, image `falkordb/falkordb:v4.22.1`) is correctly
  limited: `TIMEOUT_MAX 60000`, `TIMEOUT_DEFAULT 20000`,
  `QUERY_MEM_CAPACITY 1073741824`.
- The shared dev DB is heavily accumulated: 617-619 graphs, `used_memory_human
  793.70M`, historical `used_memory_peak_human 2.99G`.
- The Docker Desktop VM reports only `Mem: total 1967 MB`, `available 685 MB`,
  `Swap: 4096 MB used 385 MB` (measured from the QA container right after run 1).
- A live probe immediately after the run succeeded: a tiny graph
  `GRAPH.COPY qa_p028_probe qa_p028_probe_dst` returned `OK` (probe graphs
  deleted). A targeted re-run of the whole what-if file in a fresh clone against
  the same DB passed: `5 passed in 3.30s`, exit 0.
- Conclusion: run-1 failure is consistent with transient memory pressure on the
  shared, long-lived dev DB under a ~4 minute full-suite load (fork needs
  headroom); it is not reproducible in isolation. It is **not** evidence of a
  lock/install defect, but it also means the gate did not pass in the prescribed
  environment on the first attempt. A clean fresh DB matching `ci.yml` is used in
  the supplementary run to separate this environmental factor from the P-028

instead of the expected kill exit code 7. Deterministic control runs in the same
clone:

- `FALKOR_PORT=6380` -> `1 failed in 0.71s`, exit 1.
- `FALKOR_PORT=6379` -> `1 passed in 0.65s`, exit 0.

So the clean-clone gate is green only when the database is on the default port,
which is exactly how `ci.yml` provisions it (127.0.0.1:6379). Recorded as finding
L-2; QA made no test or source edits.

`block` in < 1 s, and asserts `check_invariants == []`. It does not replace the
20k/60k `make check-perf` acceptance (per the file's own docstring).

### D. Adversarial probe - tampered lock in a scratch copy (never the repo)

Plan (scratch copy only, inside container B):

```bash
docker exec pedigree-p028qsb bash -lc "rm -rf /adv && git clone --no-hardlinks /src /adv"
# line 226 is the falkordb [[package]] version line (line 1200 is starlette 1.8.0 - not touched)
docker exec pedigree-p028qsb bash -lc "sed -i '226s/1\.8\.0/9\.9\.9/' /adv/uv.lock && sed -n '224,227p' /adv/uv.lock"
docker exec -w /adv pedigree-p028qsb bash -lc "uv lock --check; echo lock-check-exit=$?"
docker exec -w /adv pedigree-p028qsb bash -lc "uv sync --frozen --extra dev > /tmp/adv-sync.log 2>&1; echo frozen-sync-exit=$?"
```

RESULT: no silent re-resolution, confirmed adversarially in three ways.

1. **Control:** untouched scratch clone, `uv lock --check` -> `base-lock-check-exit=0`
   (`Using CPython 3.12.15 ... Resolved 61 packages in 10ms`).
2. **Tampered lock** (`/adv`, line 226 `falkordb 1.8.0 -> 9.9.9`, `git diff --stat`
   shows exactly that one line changed; the real repo was never touched - `/src` is
   mounted read-only and this was a clone):
   - `uv lock --check` -> **exit 2**:
     `error: Failed to parse `uv.lock` ... The entry for package `falkordb` (9.9.9)
     has wheel `falkordb-1.8.0-py3-none-any.whl` with inconsistent version (1.8.0),
     which indicates a malformed wheel.`
   - `uv sync --frozen --extra dev` -> **exit 2**, same parse error; nothing was
     installed.
3. **Manifest drift with a valid lock** (scratch clone `/adv` and a second clone
   `/adv2`; `pyproject.toml` changed while `uv.lock` still pins 1.8.0):
   - First attempt used `falkordb==1.8.1` (not a published version): `uv lock --check`
     -> exit 1, and its message was a resolution failure
     (`no version of falkordb==1.8.1 ... requirements are unsatisfiable`) - correct
     behaviour, but it conflates drift with an impossible version.
   - Repeated cleanly with a **real** version `falkordb==1.7.0` in `/adv2`:
     `uv lock --check` -> **exit 1**:
     `error: The lockfile at `uv.lock` needs to be updated, but `--check` was provided.`
     `uv sync --frozen --extra dev` -> **exit 0**, and it installed
     `+ falkordb==1.8.0` (the locked version; the 1.8.1 attempt installed 1.8.0 too).
     So `--frozen` never resolves fresh versions - the lock is authoritative - but by
     itself it does **not** error when the manifest and lock disagree; only an
     explicit `uv lock --check` (or `--locked`) detects drift.

The two repository gate paths run the check immediately after the frozen sync
(`scripts/clean_clone_check.sh:16-17`, `.github/workflows/ci.yml:46-47`), and the
clean-clone runs above passed it. The non-gate installs (`Makefile setup`,
`scripts/quickstart.sh`, `scripts/quickstart-windows.ps1`, `Dockerfile`) rely on
`--frozen` alone, so a future manifest edit without a relock would not fail those
installs; they would deterministically install the older locked set (no fresh
resolution, no supply-chain drift). Recorded as finding L-1 (Low).

## Findings (severity)

- **L-2 (Low, test-suite portability).** `tests/integration/test_revoke_resume.py::
  test_kill_process_then_resume` strips `FALKOR_PORT` from the crash driver's
  environment (line 164) while `_crash_driver_revoke.py` uses default settings, so
  the driver always dials port 6379. The clean-clone gate therefore fails
  (`assert 1 == 7`, `NotFoundInGraph: unknown id`) whenever the database runs on a
  non-default `FALKOR_PORT` - reproduced deterministically (6380: 1 failed/exit 1;
  6379: 1 passed/exit 0 in the same clone). CI and both green runs use 6379, so the
  P-028 contract is unaffected; the documented `FALKOR_PORT` override is not usable
  for this test. QA did not edit tests.
- **L-1 (Low, configuration hygiene).** `--frozen` alone does not fail when
  `pyproject.toml` and `uv.lock` drift; it deterministically installs the locked
  versions (verified: exit 0 while `uv lock --check` exits 1). The two gate paths
  (`clean_clone_check.sh`, `ci.yml`) run `uv lock --check` immediately after the
  frozen sync and therefore catch drift; `Makefile setup`, `scripts/quickstart.sh`,
  `scripts/quickstart-windows.ps1` and `Dockerfile` do not. Recommendation (not done
  by QA - no source edits): add `uv lock --check` after those syncs or switch them
  to `uv sync --locked`.
- **Observation O-1 (environment, informational).** Under a ~4-minute full-suite
  load the shared dev DB (619 graphs, ~800 MB used, 2.99 GB historical peak) on a
  Docker Desktop VM with ~2 GB total RAM returned `GRAPH.COPY failed, could not
  fork`, surfacing as typed HTTP 503 for the what-if route. Recorded in full above;
  did not reproduce on rerun (same command, 803 passed) and not reproducible in
  isolation. This is DB-host resource pressure, not the lock/install contract.
