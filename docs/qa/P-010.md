## 3. EXPLAIN classification over every query constant (84 entries)

### 3.1 Classification table

Probe: fresh tenant graph → `ensure_schema` (so `:Node(id)` exists and is OPERATIONAL) → one
`GRAPH.EXPLAIN` per constant with dummy params (`UNWIND`/`WITH` variables need none; pattern-bound
`$params` get dummies). "Ops" = scan/join operators observed in my plan dump
(`logs/explain-all-plans.jsonl`).

Legend — class / justification:
- **INDEX-REQ** — anchored by a per-row `id` (single param or `UNWIND $ids`); the whole point of
  P-010; must show the `:Node` index and never a label scan.
- **INDEX-ALT** — lookup on a non-id indexed property (`Memory/Action.artifact_key`,
  `Revocation.root_id|state`, `Source.uri|content_hash`, `Tenant.id`); the index expected here is
  the corresponding secondary index, not `Node(id)`; still must not be an O(N) label scan.
- **SCAN-OK** — whole-population aggregate/invariant/report/UI/what-if scan by design: touching
  every node is the query's purpose, and it runs once per audit/report/UI request, not per id.
- **MIXED-OK** — deliberate whole-label scan with per-row index probes for parents (invariant);
  the per-row lookups are index-backed.
- **CREATE** — no MATCH, nothing to index.
- **DDL** — `CREATE INDEX` statements; `GRAPH.EXPLAIN` rejects them (`plan must be an array`,
  caught and reported, not a failure).
- **N/A** — `Q_COPY` is intentionally `None` (GRAPH.COPY via the client helper); `Q_INDEXES`
  is a procedure call.
