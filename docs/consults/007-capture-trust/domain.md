# 007 - Authority separation: how a *trusted* assertion is distinguished from an untrusted one

**Answer: hybrid, structural-first (option 2 carries the weight, option 1 is the minimum viable authority channel, option 3 is the honest fallback).**
1. **Structural rule (no new credential, load-bearing):** the agent channel may only *downgrade*. Drop `by` from `pedigree_corroborate` and `integrity` from `pedigree_record_source` / `POST /v1/events`; the engine sets `by='agent'` and `integrity=default_integrity(kind)` server-side. Upgrades (`by in {human,scanner}`, `integrity='trusted'` on an untrusted-kind source, `reinstate`, `revoke`) are **not expressible** from the agent channel.
2. **Separate credential where one exists:** a second registry token with `role='human'` (`PEDIGREE_HUMAN_TOKEN`), accepted only on `/v1/corroborate`, `/v1/sources`, `/v1/revoke`, `/v1/reinstate`. The UI reads it from the same env the human already has; the agent's MCP config does not.
3. **UI-only claim as documented fallback:** with no second token the UI posts `by='human_ui'`, which the gate treats as **untrusted** (same as `agent`) and the UI labels "self-asserted, not verified". Never a silent upgrade.

## Evidence actually read (all fetched 2026-10-15)

- **W3C PROV-DM** (REC 30 Apr 2013, https://www.w3.org/TR/prov-dm/): §5.3.1 "An agent is something that bears some form of responsibility for an activity taking place, for the existence of an entity, or for another agent's activity", with three types `Person` / `SoftwareAgent` / `Organization`; §5.3.2 Attribution is "the ascribing of an entity to an agent"; §5.3.4 Delegation is "the assignment of **authority** and responsibility to an agent ... to carry out a specific activity as a delegate or representative". So "who asserts" is a **first-class typed identity plus a relation between agents** - not a free-text data property - and PROV-DM contains **no authentication** of that identity. §1 only claims provenance "can be used to form assessments about its quality, reliability or trustworthiness". A system with no second principal records `actedOnBehalfOf` and does not verify it.
- **in-toto** (spec v1.0.0, https://in-toto/docs ... raw in-toto-spec.md): §1.5.4 "**Step authentication**: the actor who carries out different steps within the supply chain provides evidence of the step using an **unforgeable identifier**"; §1.5.4 "**Task and privilege separation**: ... if Alice is the only functionary allowed to tag a release, releases tagged by Bob will not be trusted"; §2.1.2 "A functionary is **uniquely identified by the public key** that they will use to sign a piece of link metadata". Attestation framework (https://github.com/in-toto/attestation spec/README.md): "An in-toto attestation is **authenticated metadata**"; the Envelope layer "handles authentication and serialization"; "To obtain predicate information that is authenticated, consumers MUST parse the Envelope's `payload`, and verify it against its `signatures`." Decisive for us, §4.3.1 demotes a self-asserted descriptive field: "in a case where a functionary's key is compromised, this field can easily be forged ... and thus it should **not be trusted for security checks**."
- **Sigstore** (https://docs.sigstore.dev/about/overview/): "Sigstore addresses these problems by helping users move away from a key-based signing approach to an **identity-based** one"; Fulcio "verifies this token and issues a short-lived certificate **bound to the provided identity and public key**"; verification requires "verify the identity in the certificate matches an expected identity". Where no key and no OIDC identity exist, there is nothing to verify. Quoted there from D. Lorenc: "Signatures can guarantee a file has not been tampered with, but they can't guarantee the file arrives at all. To be safe, your systems should be designed to **fail closed** rather than open."
- **SPDX 3.0.1** (https://spdx.github.io/spdx-spec/v3.0.1/...): `CreationInfo.createdBy` -> `Agent` (minCount 1); `Agent` "represents anything with the potential to act on a system" and carries an optional `verifiedUsing` -> `IntegrityMethod`. The SBOM author is a typed agent with an *optional* verification hook; the spec never makes the author string authoritative.
- **Biba** (https://en.wikipedia.org/wiki/Biba_Model, §Features - secondary source, primary Biba 1975 MTR-3153 not opened): "The \* (star) Integrity Property states that a subject at a given level of integrity must not write to data at a higher level of integrity (**no write up**)"; "users can only *create content at or below* their own integrity level". **Yes, (c) is a standard notion and it is exactly asymmetric**: write-down (downgrade) is free; write-up (upgrade) requires the subject to already hold the higher level, i.e. authority.
- **FIDES** (arXiv 2505.23643v2, fetched today): integrity lattice `T ⊑ U`; "Initial system and user messages are typically trusted and public and are labeled ⊥ by default"; "We ensure that all untrusted tools have **trusted wrappers**, so that we can assume that all tools label their outputs correctly"; "By enforcing P-T (but not P-F) we allow any flow as long as it is initiated in a **trusted context**. This corresponds to a form of **robust declassification**." Labels are assigned by a trusted component, never by the data; declassification is a trusted-authority act.
- **Local:** `src/pedigree/engine/ingest.py:350-352` `corroborate(..., by: str = "agent")` validates only membership in `("agent","human","scanner")` - no authority check; `:132-134` `record_source` accepts any explicit `integrity`; `mcp_server.py:128-133` passes the caller's `by` straight through; `api/routes/engine.py:115-120` same over REST; `api/auth.py:48-66` `authenticate()` resolves exactly one tenant per token, no role. `engine/gate.py:20` `TRUSTED_SUPPORT = {"human","scanner"}` and `:126-133` `supports()` are what make the forged `by` load-bearing. KNOWN_ISSUES 11 records this as open/high. docs/01 §6.5 "Adapters may override" is the only legitimate override path.

## Why not the single-option designs

Pure **separate role/credential** alone leaves `by`/`integrity` in the agent schema, so a forgotten call site re-opens the hole (that is how F-11 happened). Pure **structural rule** alone is correct but leaves the human with no way to assert anything in the single-token demo. Pure **UI-only claim** is exactly what in-toto §4.3.1 says not to trust for security checks. The hybrid makes the structural rule the default and the credential the upgrade path.

## Smallest failing-then-passing test

`pedigree_corroborate(memory_id, source_id, by="human")` with the tenant token: today `{"ok": true}` and `gate.supports()` then counts the node as trusted-supported; after the change the parameter is absent from the tool schema and the REST call returns `forbidden`. Counter-assertion: the same call with the human token returns `ok`, and `check_action` on the resulting `preserved` node returns `allow` with `preserved_lineage`.

## Confidence

**V** on every code/spec fact and on all quotes above (fetched today). **D** on Biba (Wikipedia only). **U** on judge expectations - that is judgement, not evidence. Prior art on *this specific question* is **thin**: no cited agent-memory system (PACMI, MAP-Graph, Graphiti, the seven in-event entries) separates authority at all; they record an actor string and move on.

## Risks / edge cases

- The demo must still run with one token, so `human_ui` must exist and must be visibly labelled; otherwise the hackathon demo breaks.
- docs/01 §6.5 "Adapters may override" must be re-scoped to the human channel, or the adapter becomes the bypass.
- KNOWN_ISSUES 11 does not close in the single-token configuration; it is downgraded from "high" to "documented limitation".
- A human who pastes the tenant token into the agent's environment can still forge `by='human'`. The rule binds the **agent**, not the tenant operator.

## What would change my mind

Evidence that the UI already holds a session credential distinct from the bearer token (then bind authority to that session rather than minting a second token); or a measurement that no human-in-the-loop corroboration is needed for the demo, in which case the structural rule alone suffices and the second token is deferred.
