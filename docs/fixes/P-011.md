# P-011 — Recoverable revoke: resume `running` Revocations (FIX_PROMPT B1)

Status: spec (2026-10-16). Loop: SPEC -> red tests (crash/fault injection) -> implement ->
`make check` -> dogfood -> QA (`docs/qa/P-011.md`) + red-team if surface changes -> docs -> commits.

## Problem (verified in-tree)

- `engine/revoke.py:132-145`: when `Q_REVOKE_ROOT` matches no row (root already
  `revoked`/`running`), `revoke()` returns `{"idempotent": True, ...}` — even when the latest
  Revocation row is still `state='running'`. A revoke that died mid-flight (timeout/crash)
  therefore can never be finished by calling `revoke()` again: it is a no-op forever.
- `resume_incomplete()` (`revoke.py:299-308`) exists and its docstring says "called on startup
  and by /readyz tooling", but there are **zero call sites** outside its definition.
- Crash window (by design): root row is created first; descendants get quarantined (excluded
  from retrieval); `_finish` flips the row to `done` last — so recovery = re-running
  `resolve()` + `_finish()` for that row. `resolve()` is already idempotent (re-quarantine +
  recompute + write final); chunk writes must be restartable (verify in tests).

## Fix plan

1. `revoke()`: in the no-row branch, if the latest Revocation `state == 'running'` — resume it
   under the tenant lock (`resolve(...)` + `_finish(...)`) and return the finished result with
   `"resumed": True`; `done`/`reinstated` keep the current idempotent response.
2. Startup recovery: in the app lifespan, run a **bounded background** pass over active
   registry tenants calling `resume_incomplete()` per tenant (only when a `running` row
   exists); log a one-line summary per tenant. Never blocks readiness.
3. `POST /v1/admin/resume` (X-Admin-Token + body `{ "tenant": "<id>" }`) -> runs
   `resume_incomplete` for that tenant, returns the summaries; CLI `pedigree resume [--tenant ID]`
   (all active tenants when omitted) for operators.
4. Keep P-012/P-024 interplay in mind: resume only re-derives from **revoked roots**
   (`revoked_roots()`), which stays correct until B2 changes reinstate; note the shared helper
   if B2 introduces one.

## Tests first (per FIX_PROMPT B1)

1. **Fault injection (in-process)**: patch the writer so `Q_WRITE_FINAL` raises after chunk 1 of
   >=3; assert row `running` + nodes `quarantined`; call `revoke()` again -> final statuses
   equal hand-computed expectations for the scenario, row `done`, `check_invariants == []`.
2. **Kill-process**: subprocess driver (test-owned script) runs a revoke on a >=3-chunk
   workload and `os._exit(7)` after the first final-write chunk (patched `Db.query` counting
   ops); fixture asserts exit 7; then a fresh process/`resume_incomplete` finishes it -> same
   expected statuses.
3. **Crash between barrier and fixpoint**: crash right after the quarantine loop, before any
   final write; recovery -> expected statuses.
4. `revoke()` on a `running` row resumes (not "idempotent no-op"); on a `done` row stays the
   current idempotent response.
5. `/v1/admin/resume` + `pedigree resume` CLI: end-to-end on a crashed tenant.

Oracle note: the independent from-scratch oracle lands with P-012 (`tests/oracle.py`); P-011's
tests use explicit hand-computed expectations on small graphs plus invariants, and MUST be
re-pointed at the oracle once it exists (note in P-012 spec).

## Acceptance (FIX_PROMPT B1)

- Oracle/hand-computed equality in all three crash tests; `check_invariants == []`;
  `revoke()` and `POST /v1/admin/resume` + CLI recover a `running` revocation; `make check` green.
