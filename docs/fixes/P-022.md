# P-022 — Observability: visible trace, metrics, structured logs

Status: in progress (Phase E, Sat 2026-10-17). Source: `FIX_PROMPT.md` PHASE E item E2.
Owner: feature session.

Observability is deliberately narrow: it may count, time and label *operations*,
never beliefs or credentials.

## Acceptance

1. **Trace in responses.** `trace` — a list of `{op, ms, rows}` — is returned by
   `POST /v1/revoke`, `GET /v1/blame/{id}`, `GET /v1/impact/{id}`, `POST /v1/gate`
   and by the matching MCP tools (`pedigree_revoke`, `pedigree_blame`,
   `pedigree_impact`, `pedigree_check_action`). The trace covers the action's own
   database operations, not authentication/registry lookups. Entries come from the
   existing `db.client.Trace` (the engine already threads `trace=` through the
   revocation, blame, impact and gate paths); the transport creates the trace, passes
   it, and attaches `out["trace"] = trace.as_list()`. The key is additive: existing
   clients are unaffected. No trace entry contains an id, a reason or a token.
2. **Metrics** on the existing admin-protected `/metrics` (protection unchanged):
   - `pedigree_query_seconds{op}` histogram — observed for every `Db` operation;
     `op` is a static code-defined name.
   - `pedigree_revocations_total{status}` counter — `done` | `resumed` | `idempotent`
     from the revoke outcome; counted inside `engine.revoke.revoke` so both
     transports are covered. Dry runs are not counted.
   - `pedigree_gate_decisions_total{decision}` counter — counted inside
     `engine.gate.check_action`; `decision` is the value the gate result carries
     (`allow` | `warn` | `reverify` | `block`).
   - `pedigree_nodes{tenant,status}` gauge — refreshed whenever a tenant's report is
     served (`/v1/stats`, `/v1/graph`, MCP `pedigree_report`). This is a documented
     limitation: it is not a scrape-time scan of every tenant graph (the shared dev
     database holds hundreds of graphs; a full scan per scrape is not affordable).
3. **Structured access log.** One JSON line per request on the `pedigree.access`
   logger with `request_id` (correlation id), `method`, `path` (route template when
   routed — no query string), `status`, `ms`, and `tenant` / `op` when the request
   authenticated or admitted. Tokens are never logged: the line never contains a
   credential shape (`ped_a_…` / `ped_o_…`), which the tests assert by pattern.
4. **UI trace strip.** A collapsible strip under the influence map shows the ops of
   the last action (blame, impact, revoke preview/confirm, gate) rendered from the
   same response — no extra request. Empty state says so.

## Tests

`tests/integration/test_p022_observability.py`:
- each of the four REST endpoints returns a non-empty `trace` with `op`/`ms`/`rows`;
- each of the four MCP tools returns a non-empty `trace`;
- after one real revoke and one gate call, `/metrics` (admin header) exposes
  `pedigree_revocations_total`, `pedigree_gate_decisions_total` and
  `pedigree_query_seconds`; after a report call, `pedigree_nodes{tenant=…,status=…}`;
- the access log line parses as JSON, carries the correlation id and status, and
  neither it nor the trace contains a `ped_` token shape.

Browser evidence for the UI strip: `docs/qa/P-022-browser.md`. Independent QA pass:
`docs/qa/P-022.md`.

## Out of scope

- Changing `/metrics` protection or re-labelling existing series.
- Scrape-time per-tenant node counting (see limitation above).
- Tracing the ingest surface (record/remember/action/session) — their ops are visible
  in `pedigree_query_seconds`; the four judged actions get the response trace.
