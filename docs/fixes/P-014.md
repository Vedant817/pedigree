# P-014 — Request-wide quota admission (FIX_PROMPT C2)

Owner: Phase C. Status: implemented; independent QA and red-team PASS.
Authoritative design: [consult decision](../consults/009-p014-quota/decision.md).

## Contract and implementation

Authenticated REST and MCP creators explicitly inject the registered tenant's existing
`node_cap` as `QuotaPolicy`. Registry errors propagate; public calls never select an
unlimited fallback. Trusted standalone engine calls remain registry-independent unless
passed a policy. No cap changes, graph metadata, reservations or new dependencies.

`engine/quota.py` holds a shared Redis owner-token mutex for the complete request,
including identity-aware event planning, count comparison and all synchronous writes.
Nested engine calls reuse that context. Acquisition is bounded; the mutex has **no
expiry** and release atomically compares its opaque owner token. Mutation calls check
known ownership loss before sending the graph query. This check is not a fencing or
failover guarantee. Ambiguous mutation errors retain ownership instead of releasing
while a graph write could still be running. A definite constraint rejection releases.

Accounting preserves `node_count` (`MATCH(n)`): Source, Memory, Action, Session,
Revocation and any other physical nodes all count. Source identity follows the existing
engine exactly: normalized hash plus URI; derived URI identity only without an explicit
ID; otherwise explicit CREATE semantics. Batch planning deduplicates canonical source
identities, explicit IDs and Sessions against the graph and the current batch. URI-only
sources with explicit IDs retain their existing CREATE/conflict behavior; Memory and
Action retries retain their existing CREATE/conflict behavior.

Covered paths: sources/memories/actions; full `/v1/events` batches; Sessions and
ensure-before-READ; gate `record`; MCP equivalents; revoke and reinstate ledger creates.
Revoke/reinstate reserve room before changing root status or superseding running rows.
This deliberately means a full graph can reject a safety operation that needs another
ledger node. Dry-run and zero-growth retries remain available. Corroboration and READ
edges add no nodes and work at/above cap. Existing over-cap data is preserved and only
zero-growth admissions are allowed. What-if scratch graphs retain their separate
existing simulation bounds.

Quota rejection happens before **any event-batch mutation**, so nodes and edges stay
unchanged. Event ingestion is sequential, **not transactional**: later invalid-input or
database errors may leave earlier events committed. No rollback is claimed.

## Coordination assumptions and recovery

Supported operation requires one stable Redis/Falkor primary, coordination keys protected
from eviction/loss, and every public creator cooperating with this boundary. Shared DB
credentials can access the coordination namespace; future tenant ACLs must allow the
required mutex commands and protect other tenants' keys. Redis restart, failover,
FLUSH/key loss or operator removal while writers run can invalidate coordination and
requires coordinated shutdown/recovery. No distributed failover safety is claimed.

Crash/ambiguous-write availability tradeoff: `pedigree:quota:mutex:<full graph name>`
remains stranded, with later acquisitions returning unavailable after the bounded wait.
There is no automatic stealing, expiry or reset. To recover, an operator must stop all
writers using the tenant/primary, establish that outstanding graph work is quiescent,
inspect the tenant's actual graph and cap, then delete **only the exact tenant mutex
key** before restarting writers. An absent process alone does not prove DB quiescence.
Never remove mutex keys by a broad scan or while any writer might still execute.

## Builder evidence and test scope

Tests-first regression command:
`.venv/Scripts/python.exe -m pytest tests/integration/test_core_scenario.py -q`
returned `12 failed in 2.26s`, each from the interrupted implementation's registry
lookup on standalone graphs. The first new quota test run failed collection because
`pedigree.engine.quota` did not exist. A further tests-first reinstate ledger regression
returned `1 failed, 10 deselected in 1.65s` (missing quota rejection) before its fix.

Builder checks are development evidence, not independent QA certification. Tests in
`tests/integration/test_p014_quota.py` exercise real FalkorDB: exact-fit/overflow graph
snapshots, canonical identities and aliases, session-only batches, retry-at-cap,
REST/MCP/gate parity, ledger barriers, zero-growth edges, independent interpreter
process contention, process-crash stranding and ambiguous write fail-closed behavior.
`tests/unit/test_quota.py` exercises owner-only unlock, known ownership loss, nested
reuse, policy binding and coordination failure. Run these plus the standalone/core,
events and MCP regressions before acceptance. Independent QA must supply its own
commands, actual output, adversarial cases and verdict; this spec grants no PASS.
